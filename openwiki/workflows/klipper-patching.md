# Built-in Klipper patching

Forge-X **keeps the printer’s stock host Klipper** at `/opt/klipper/klippy`; it does not build or install a complete upstream Klipper tree. Instead, each normal mod initialization overlays a small, version-sensitive set of replacement modules, compiled host helpers, and extra plugins onto that stock tree. This is the project’s mechanism for carrying printer-specific fixes while retaining the native MCU firmware and making uninstall reversible.

> **Hardware-risk boundary:** a patch can apply mechanically yet be incorrect for a supported stock firmware layout or unsafe in a motion/calibration workflow. Do not edit deployed `/opt/klipper` files as a durable fix; update the overlay and validate on the relevant printer/firmware combination.

## Lifecycle and ownership

The normal initializer, [`.shell/init-main.sh`](../../.shell/init-main.sh), binds the real `/opt/klipper` into the Buildroot environment during `init_buildroot`, then calls `apply_klipper_patches` before configuration repair and service startup. The target is therefore the stock-side `/opt/klipper/klippy`, not a copy inside the chroot.

```text
Repository overlay                    Stock host tree
.py/klipper/plugins/**    ──symlink→ /opt/klipper/klippy/extras/**
.py/klipper/patches/**    ──symlink→ /opt/klipper/klippy/**
                                          └─ original replacement: <file>.bak

boot: plan user packages (read-only) → cleanup stale and unplanned user links
      → link built-in files → add or retarget only differing user links
      → write the config aggregate only if it changed → start Klipper later
uninstall: restore adjacent backups via owned links, even without sources
```

[User packages](user-klipper-plugins.md) in `mod_data/plugins/` are layered after
the built-in overlay through the existing overlay library. Their optional configs,
extras and permitted Forge-X patch overrides are independent. Override priority
does not modify stock backups. Stock boot preparation clears only the generated user config aggregate;
Python links are left in place.

The complete filesystem operation is implemented by `.bin/exec/overlay`.
`.shell/klipper_overlay.sh` only preserves the shell entry points used by normal
initialization and uninstall; it contains no link/restore policy. Native source,
build/publish scripts and component lifecycle/C++ tests belong to ForgeX Private
under `src/overlay`. The public tree keeps the ARM executable and product
integration tests. Canonical commands are `overlay install` and `overlay uninstall`.

When invalidating bytecode, the utility distinguishes a cache directory from an
older regular file named `__pycache__`. It preserves non-directory entries while
restoring the actual module from its stock backup. Real cache directories,
including directory aliases, lose only the corresponding module's tagged `.pyc`
files; unrelated entries remain. Adjacent `.pyc`/`.pyo` files are also removed.
Directory access/read failures are reported rather than treated as an empty cache.

The process is idempotent in the normal supported case:

1. **Clean obsolete overlay entries.** The patcher scans symlinks under the target tree. A Forge-X link is retained only while its exact source-to-target mapping remains current. Stale Forge-X links and any broken link are removed, first restoring a neighboring `.bak`, `.backup`, `.old`, or `.orig` regular file when one exists. Live external symlinks are left alone.
2. **Install plugins.** Every non-hidden regular file below [`.py/klipper/plugins/`](../../.py/klipper/plugins/) is symlinked at the same relative path below stock `extras/`. Parent directories are real directories, allowing package files to coexist with an existing Klipper directory and to be managed independently. Python bytecode and `__pycache__` content are excluded.
3. **Replace stock modules and host helpers.** For each supported `.py` or `.so` file below [`.py/klipper/patches/`](../../.py/klipper/patches/), the patcher preserves the stock target as `<target>.bak` once, removes a prior non-symlink target if necessary, and symlinks the repository file into its original relative path. It creates parent directories for nested replacements and ignores generated bytecode. Other file types are not installed from the replacement tree.

When upgrading from the former in-place tuning mechanism, the first `toolhead.py` backup may already contain `LOOKAHEAD_FLUSH_TIME = 0.150`. The overlay recognizes that exact legacy value and normalizes the backup to the stock `0.5` so later cleanup or uninstall remains a complete rollback. It does not otherwise rewrite backups.

Because patch files are linked rather than copied, a later boot points the installed stock tree at the updated repository overlay. It also means an arbitrary manual edit to a linked target edits repository-backed content or is lost when the link is refreshed; use source changes instead.

## What belongs in each overlay area

| Area | Deployment model | Purpose and examples |
|---|---|---|
| [`patches/`](../../.py/klipper/patches/) | Replaces an existing Klipper module or host helper; original retained as `.bak` | Core/config parsing and G-code handling; selected `extras` modules; `mcu.py` and `toolhead.py` runtime tuning; the matched adaptive-PA Python/CFFI modules and `c_helper.so`. |
| [`plugins/`](../../.py/klipper/plugins/) | Adds files below `klippy/extras/` while preserving their relative paths | Forge-X-specific objects loaded through configuration: `mod_params`, `resurrection`, Feather screen packages, `load_cell_tare`, `md5_check`, and `tone_player`; see [Forge-X Klipper extensions](klipper-extensions.md) for their activation, purposes, and commands. |

A replacement must retain the exact stock module path expected by the target firmware. Additions should normally be plugins; do not use a replacement patch merely to introduce a new Forge-X module.

### Patch intent is source-local

[`patches/webhooks.py`](../../.py/klipper/patches/webhooks.py) keeps the Stock screen connected across `RESTART`, `FIRMWARE_RESTART`, and `SAVE_CONFIG`.

The replacement files carry short `Changes:` headers where applicable. Examples include:

- [`patches/gcode.py`](../../.py/klipper/patches/gcode.py) normalizes the raw command used for `M117`/`M118`, and its history includes non-ASCII object-name fixes.
- [`patches/extras/virtual_sdcard.py`](../../.py/klipper/patches/extras/virtual_sdcard.py)
  excludes hidden files/directories during G-code file enumeration and
  publishes total print-time metadata from legacy and OrcaSlicer footers.
- [`patches/extras/gcode_shell_command.py`](../../.py/klipper/patches/extras/gcode_shell_command.py) adds Forge-X background/exclusive execution parameters.
- [`patches/extras/temperature_sensor.py`](../../.py/klipper/patches/extras/temperature_sensor.py) adds a G-code action for out-of-range sensor values.
- [`patches/extras/shaper_calibrate.py`](../../.py/klipper/patches/extras/shaper_calibrate.py) drains a ready child-process result before waiting for the child to exit. Recent history documents why: a result larger than the OS pipe buffer could otherwise block `SHAPER_CALIBRATE` indefinitely.
- [`patches/extras/probe.py`](../../.py/klipper/patches/extras/probe.py) closes locally owned multi-probe lifecycles in `finally`, including probe, tolerance, and retract failures. The matching published source is in [klipper-ad5m commit `c0b26da`](https://github.com/DrA1ex/klipper-ad5m/commit/c0b26daa5a54de73fe70619e1e6294149ce2b4c4), following [PR #93](https://github.com/DrA1ex/ff5m/pull/93); the behavioral tests remain in Forge-X.
- `patches/kinematics/extruder.py`, `patches/chelper/__init__.py`, and `patches/chelper/c_helper.so` retain the matched adaptive pressure advance host API. The helper also carries the serial-queue timing backport. It is soft-float ARM EABI and depends only on the stock `libc.so.6`; it is not MCU firmware and does not use Forge-X's `libstdc++` runtime bundle.

Keep an explanation close to the changed behavior in the file or commit. The wiki should not become a speculative inventory of every line-level divergence from stock Klipper.

## Patch provenance and verification

[`docs/klipper-ad5m-manifest.json`](../../docs/klipper-ad5m-manifest.json) pins
the replacement sources to `d7da8a94eb9f4d464c5e98863d36f2387e8af4eb` in the
[DrA1ex/klipper-ad5m](https://github.com/DrA1ex/klipper-ad5m) history. All 26 shipped
Python replacements match that snapshot byte for byte. The template-cache
snapshot is prepared locally; publish its corresponding history commit together
with this overlay update before release. The manifest also
records the SHA-256 of the rebuilt `c_helper.so`; the fork stores its C sources,
not the prebuilt binary.

The `extras/gcode_macro.py` replacement persists compiled Jinja templates using
Jinja's filesystem bytecode cache. Its source checksum detects changed macros
without relying on file timestamps; Python/Jinja versions and the loaded module
identity separate incompatible compilers. Macro parameters, variables, printer
status and action callbacks are evaluated on every invocation. `RESTART` reloads
changed configuration using the existing interpreter; a hard process restart is
required after deploying changed Python implementation files. Missing, truncated
or unwritable cache data falls back to normal compilation. Cache files under the
configuration directory's `.cache/gcode_macro/` are disposable derivative data.
Compare this copied module with the supported stock Klipper version when updating
Klipper, and rerun `tests/test_gcode_template_cache.py` on the supported runtime.

The three UART changes after the previous snapshot `dfd1945` are:

- [`4944975`](https://github.com/DrA1ex/klipper-ad5m/commit/494497507f639b29aadcc7234ad9c38d568ea284):
  `serialhdl.py` falls back to the connection's configured baud rate when
  the MCU identify dictionary omits `SERIAL_BAUD`. This gives serialqueue
  the wire frequency needed to account for transmission time.
- [`4375de3`](https://github.com/DrA1ex/klipper-ad5m/commit/4375de3a2530aa5a49eb15f7ddda95528e9dbf9c):
  UART sessions fall back to a 192-byte `RECEIVE_WINDOW` when the dictionary
  omits it. The commit records disassembly of `serial_rx_byte()` in stock
  `Mainboard-20230831.bin` and `Eboard-20231012.hex`: both accept buffer indices
  through `0xbf`, with buffers at `0x200001b0` and `0x20000140`, respectively.
  The host can therefore use its existing byte-based receive-window limit
  alongside `MAX_PENDING_BLOCKS`, without changing MCU firmware. This evidence
  applies to those stock images; recheck the buffer before reusing the fallback
  with different MCU firmware.
- [`ce2ec15`](https://github.com/DrA1ex/klipper-ad5m/commit/ce2ec150b510ec4119c09e3d7fc5b1f059d8c386):
  upstream [`2e5802370c1a`](https://github.com/Klipper3d/klipper/commit/2e5802370c1a)
  reduces `MIN_REQTIME_DELTA` from 250 ms to 100 ms in `serialqueue.c`. The
  shorter early-send horizon avoids flushing many small UART blocks while
  the MCU move queue is saturated. This change requires the rebuilt helper;
  installing only `serialhdl.py` does not apply it.

Firmware-provided baud rates and receive windows take precedence. The
fallbacks apply only to sessions marked as UART (`serial_fd_type == b'u'`),
and each fallback is logged. CAN frequency selection remains unchanged.
These changes are unconditional host fixes, independent of `tune_klipper`.

The snapshot is on `opt/lazy-multiprocessing-imports`, two commits after
`main` at `4375de3`. Both are shipped:

- [`219e99c`](https://github.com/DrA1ex/klipper-ad5m/commit/219e99c435d80e1fe0733349fc350d944ef49f3a)
  moves the `adxl345.py` multiprocessing import into accelerometer CSV export.
- [`6ea380d`](https://github.com/DrA1ex/klipper-ad5m/commit/6ea380d0e082a7ad6cae1bb97c0a5b540d340e2f)
  moves the `shaper_calibrate.py` import into background calculation, after
  the direct-call path for offline tools.

The fork measured about 706 KiB additional PSS for importing multiprocessing
alone on ARMv7/Python 3.7 (ten-run mean). This is import overhead, not a measured
whole-Klippy saving; the two changes are not additive. An operation that needs
the module still loads it, and it remains loaded afterward. Process creation,
calculation results, errors, and CSV formatting are unchanged.
`tests/test_klipper_lazy_multiprocessing.py` checks clean-interpreter imports,
offline calls, CSV export, and a real forked calculation with a result larger
than the pipe buffer and a child error.

The host patch inventory was compared against the fork's stock commit across
`main` and the deferred-import branch. The startup GC and immutable-config
changes from `experimental-gc` are already included through `1c21f43`; its
older tree must not replace the newer host fixes. `garbage_collection.py` is
shipped separately as a plugin. The MCU sources on `mcu-v0.11` are a separate
firmware development branch, not a host overlay update.

Adaptive Pressure Advance is already published in
[`4f41d5d`](https://github.com/DrA1ex/klipper-ad5m/commit/4f41d5df9c9fc6b4105b61633224d8f4dae95ff3),
the backport of upstream `c84d78f3f169bc5163d11b74837f9880b0b7dba4`.
It includes `kinematics/extruder.py`, the CFFI declarations in
`chelper/__init__.py`, and the time-indexed PA history in `kin_extruder.c`.
The Forge-X Private build inputs under `src/klipper_c_helper/source/klippy/`
match the corresponding fork files, including the serial-queue update. Build
with `src/klipper_c_helper/build.sh`, run `src/klipper_c_helper/test.sh`, and
copy only `exec/klipper/c_helper.so` into `.py/klipper/patches/chelper/`.
The build checks ARM EABI5 soft-float, the sole `libc.so.6` dependency, and
stock-compatible GLIBC symbol versions. Keep the PA Python modules and helper
API together when updating either backport.

The helper is tracked at `.py/klipper/patches/chelper/c_helper.so` in the
Forge-X repository. `sync.sh` includes it in both full and lightweight archives:
`--skip-heavy` excludes `.bin`, not `.py/klipper/patches`. `sync_remote.sh`
replaces `.so` files using a neighboring temporary file and atomic rename,
preserving the inode mapped by the running process until it exits. Copy or
rename failure keeps the old helper and removes the partial temporary file.
The overlay then preserves the stock helper as `.bak` and links
`/opt/klipper/klippy/chelper/c_helper.so` to the deployed patch.

Use the `klipper` sync profile when deploying a changed helper: it reloads the
overlay and hard-restarts Klippy. The CFFI library is cached in the process,
so an in-process `RESTART` alone does not load a new helper. Other profiles
still transfer the file, but their restart policy may leave the old library
active until a full process restart. `tests/test_klipper_sync.py` checks archive
inclusion, profile flags, loaded-inode preservation, idempotence, and failed
copy/rename recovery without connecting to a printer.

Verify the shipped inventory and hashes offline, then compare Python sources
against the manifest's exact published commit:

```shell
.venv/bin/python tests/verify_klipper_fork.py
.venv/bin/python tests/verify_klipper_fork.py --fork https://github.com/DrA1ex/klipper-ad5m
```

The fork check must report no source mismatches. It does not compare the
binary with the fork, which does not contain it; verify its build inputs and
ABI separately. After updating sources and rebuilding the helper, regenerate
the inventory with `tests/verify_klipper_fork.py --update --commit <full-sha>`.
This records hashes; it does not establish correspondence to the fork by itself.

`tests/test_serialhdl_patch.py` exercises session negotiation with missing and
explicit MCU constants, CAN compatibility, and identify-timeout cleanup.
The native pressure-advance history test protects values on already-queued
moves. Hardware validation of UART timing and receive-window behavior remains
a separate step requiring an idle printer and explicit operator authorization.

## Runtime-selected tuning

`mod_params.json` declares `tune_klipper` as a boolean defaulting to on and migrates the older `fix_e0017` setting to it. Initialization fills missing settings from the schema; updates preserve an existing saved value, including `0`. The shared setting selects:

| Module | Default when disabled | Enabled value | Intended symptom |
|---|---:|---:|---|
| Patched `mcu.py`: `TRSYNC_TIMEOUT` | `0.025` | `0.05` | E0011 communication timeout |
| Patched `toolhead.py`: lookahead flush time | `0.5` | `0.150` | E0017 move-queue overflow |

Both replacement modules read `[Variables] tune_klipper` from `/opt/config/mod_data/variables.cfg` during Klipper startup. A missing file, section, key, or invalid value selects the disabled value. [`zchanges.sh`](../../.shell/commands/zchanges.sh) hard-restarts Klipper after the setting is persisted so both modules load the new selection. Neither module is modified at runtime. Do not confuse `tune_klipper` with `klipper_rt`: the latter changes Klipper scheduling and does not alter these values.

## Uninstall and recovery behavior

[`.shell/uninstall.sh`](../../.shell/uninstall.sh) implements the inverse operation before removing the mod:

1. Remove the managed plugin include from `user.cfg` through the existing config restore tool.
2. Use the overlay's cleanup in removal mode to remove owned user/built-in symlinks and restore their adjacent backups even when the sources are gone, including compiled host helpers. When a target link is missing but its Forge-X patch source survives, removal mode restores its `.bak` only if the target is absent. There is no global `.bak` scan, and regular files are not replaced by cleanup. Backups without either an ownership link or a surviving patch source are retained.
3. Remove the generated aggregate. Soft uninstall retains other user settings and package sources; hard uninstall removes `mod_data`.
4. Hard uninstall removes the nonstock `gcode_shell_command.py` and its bytecode caches even if generic rollback restored it from `.bak`.

That reversal relies on the backup convention created by the patcher. Never delete or overwrite `<target>.bak` in an installed system without a verified recovery plan. The normal dual-boot/recovery procedures remain the operator safety route; see [`docs/UNINSTALL.md`](../../docs/UNINSTALL.md), [`docs/DUAL_BOOT.md`](../../docs/DUAL_BOOT.md), and [`docs/RECOVERY.md`](../../docs/RECOVERY.md).

## Change procedure

1. **Classify the change.** Use `plugins/` for a new Forge-X extension and `patches/` only when replacing an existing native module. Record the target stock path and behavior being changed.
2. **Check target compatibility.** Compare the replacement with the Klipper module/layout shipped by each supported stock firmware. The supported firmware range is in [`docs/INSTALL.md`](../../docs/INSTALL.md); do not assume mainline Klipper is a compatible baseline.
3. **Preserve deployment symmetry.** Confirm the nested relative path works, a stock target exists to back up for replacements, stale-overlay cleanup recognizes the entry, and uninstall can restore it. Consider how removal/renaming behaves on an already patched printer.
4. **Keep settings coherent.** If a patch depends on a user setting, update the parameter schema, Klipper configuration/macro exposure, shell reaction, migration/deprecation behavior, and operator documentation together.
5. **Validate the exact feature on hardware.** A successful boot establishes only that imports/startup worked. Exercise the affected G-code, calibration, print, screen, or recovery path; inspect Klipper logs; and test the supported firmware/device combination. For tuning, test both enable and disable and confirm the reboot/restart result.
6. **Check removal.** On a controlled device or equivalent recovery scenario, verify that old links are cleaned, `.bak` restoration is possible, and the documented uninstall path returns the native host files.

Recent history reinforces this discipline: the shaper-calibration deadlock fix requires `SHAPER_CALIBRATE` testing. An earlier Python-only adaptive-pressure-advance replacement was reverted because its native helper still exposed the old API. The current backport keeps the two Python modules and `c_helper.so` together from the same upstream Klipper change; patch applicability alone is still not enough evidence of safe behavior.
